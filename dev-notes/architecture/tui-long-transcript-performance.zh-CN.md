---
title: "有界 TUI 对话渲染"
---

Tau 的 Textual 对话现在只挂载有界窗口内的消息部件，而不是让 Textual DOM 随会话中的每条消息持续增长。

## 存在原因

持久化对话和 TUI 显示状态原本已经分离，但最初的 `TranscriptView` 会为每个 `ChatItem` 挂载一棵 Textual 部件树。因此，长会话会让无关交互变得昂贵：即使用户只是在提示框中输入，Textual 也必须在布局和刷新工作期间访问数千个消息泵。

完整对话刷新开销更大，因为它会删除并重新创建每个消息部件。工具完成、结构化思考响应、结果可见性切换和终端尺寸调整都可能进入该路径。

## 架构

完整显示投影仍保存在 `TuiState.items` 中。`TranscriptView` 现在只挂载一个连续的前端窗口：

```text
CodingSession / durable messages
              ↓
TuiState.items (complete display history)
              ↓
TranscriptView window (bounded Textual DOM)
```

初始挂载最新的 200 项。较小的边界行会提示窗口之外存在更早或更晚的项目。到达边界时，窗口按较小页幅移动，同时保留一条现有消息作为滚动锚点。状态绝不会被截断，会话持久化也保持不变。

这有意作为 Textual 适配器优化实现。`tau_agent` 或 `CodingSession` 中未增加窗口化、渲染或部件策略。

## 增量高频路径

常见事件路径不再重建对话历史：

- 工具完成会更新现有工具行；
- 终端命令追加并完成一行；
- 最终有序思考/文本块只替换临时助手尾部；
- 思考和工具结果可见性只更新受影响的已挂载行；
- 终端尺寸调整依赖 Textual 原生重排；
- 对话项和工具调用查找使用前端索引，而不是反复扫描。

提示词活动动画保持流畅，但固定尺寸的动画帧会跳过布局，工具耗时行最多每秒更新一次。

## 权衡

Textual 原生 Markdown、选择、流式传输和逐消息渲染对已挂载窗口保持完整。窗口间移动会清除视口之外的部件，因此鼠标选择无法跨越分页边界。继续滚动仍可访问完整对话，导出/会话重放也仍使用完整持久化历史。

## 验证

自动化测试覆盖：

- 在保留完整状态的同时限制已挂载部件数量；
- 在对话两个方向分页；
- 滚动锚定和流式行为；
- 工具、结构化助手、结果切换和尺寸调整的增量更新；
- 节流的活动/计时器布局工作。

使用以下命令运行项目检查：

```bash
uv run pytest
uv run ruff check .
uv run ruff format --check .
uv run mypy
```

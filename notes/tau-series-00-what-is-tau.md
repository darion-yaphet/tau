# 第 0 篇：Tau 是什么——给初学者的终端 Agent 全景图

> 本文快照于 Tau 0.4.1（2026 年 9 月）。代码持续演进，函数名与行级细节以仓库当前源码为准。

“AI Agent”满天飞，不少就是聊天框边上多了几个按钮，本质还是对话。

您在网页输入框里敲一句“帮我写个贪吃蛇”，大模型吐出一屏幕代码，您再 `Ctrl+C` `Ctrl+V` 往编辑器里贴。这是补全，不是工程。真实写代码是另一回事：在祖传仓库里翻定义，改完一行冒出十个报错，在终端里跟依赖死磕，还得盯着生产环境别在周五下午出事。

要是 AI 没法直接碰这个真实世界，它就只能隔岸观火：火烧的是您的仓库，它在对岸生成建议。

**Tau 是为了把大模型从“动嘴的补全器”变成“真能读写仓库、执行命令的终端程序”。** 您在项目根目录下敲一声 `tau`，让它“解释这个仓库”“给这个模块补测试”，或者“顺着这段报错把 bug 揪出来”，它就会在模型的指挥下读文件、改代码、跑命令，并把每一步实时显示在终端里。它也支持一次性的命令行调用（print mode）：

```bash
tau -p "解释这个仓库的架构"
```

但要是仅把 Tau 当成一个好用的命令行外挂，就小看它了。Tau 还是一份写得克制、可供解剖的 Agent 参考实现。 源码把模型适配、通用 Agent 循环和终端编码产品切成三层，就是为了让人看清：剥去营销话术，一个能干活的 Agent 到底需要哪些部件。

本篇只做一件事：给一张产品和概念地图。函数级路线从下一篇开始。

## 先分清四个角色：别把功劳和黑锅都扣给模型

想搞清楚 Agent，第一步得破除迷信：神迹不是模型一个人变出来的，出了 bug 也不该只骂模型智商不够。

一次真实的编码任务里，台上有四个角色：

```text
用户     提出目标，对有副作用的改动最终负责，并在系统可能被搞砸之前取消
模型     阅读当前上下文，负责推理、生成回复，或提出下一步该调哪个工具
Agent    维护状态机与运行循环，把模型的意图翻译成可执行步骤，再把结果送回去
环境/工具 真正读写磁盘、执行 bash，并把真实输出返回
```

大模型看起来像什么都知道，可一旦放到您本地硬盘上，它就是个**纯文本预测器**：看不见仓库，也跑不了 `pytest`。

Tau 做的核心工作，就是给它装上眼睛（`read` 等读工具），装上机械臂（`write`、`edit`、`bash`），并把碰壁后的报错和命令输出原样打包成结构化数据，再送回模型。模型看到现实反馈，调整计划，接着下一次调用，直到任务完成，或您按下 `Ctrl+C`。

**这条“思考 → 行动 → 观察 → 再思考”的反馈闭环，才是 Agent 的灵魂。** 没有闭环，再能说的模型也只是补全器。

所以，别指望 Tau 是个全自动替您做完一切决策的黑盒。它更像带安全绳的工作台。模型依然会一本正经地胡说八道；您依然得把目标交代清楚，盯紧它修改的文件，并在它打算做出危险操作时拉闸。绳子在，也得有人拽着才管用。

## Tau 实际提供了什么

翻开当前的 Tau 仓库，一个实用编码 Agent 该有的家当已经齐了：

- **终端界面与脚本模式**：带交互面板的 Textual TUI，以及能管道输出、适合自动化的 print mode
- **内置编码工具箱**：为改代码打磨的 `read`、`write`、`edit`、`bash`
- **可回溯的会话**：基于 JSONL 的追加式历史，支持中断、恢复和分叉
- **斜杠指令**：`/login`、`/model`、会话管理、上下文压缩与导出
- **项目级外部记忆**：从 `AGENTS.md`、`.tau/` 与 `.agents/` 加载项目指令和规范
- **多模型接入**：主流厂商，以及任何兼容 OpenAI API 的本地或私有端点

这些东西没有堆在所谓的“Agent 大脑”里。`src/tau_coding/cli.py` 用 Typer 支起入口；`src/tau_coding/session.py` 管会话；`src/tau_coding/tools.py` 提供本地操作。它们把通用 Agent 循环安放在开发者天天用的终端里。

**Tau 自己不会凭空产生智能。** 没通过 `/login` 配置 Provider，或 API Key 停了，它就是个安静的终端程序。模型在云端推理（并消耗您的钱包）；Tau 在本地提供工具、管理记忆、画地为牢，并呈现在您眼前。

## 为什么它适合用来学习架构

市面上不少工业级编码助手，为了功能齐全，往往把模型适配、工具协议、会话历史、权限、UI 甚至遥测搅在一起。对普通用户省事，对想学架构的人却很难分清：哪些是 Agent 活下去必需的，哪些只是产品功能。

Tau 选了克制的三层，依赖只许单向流动：

```text
tau_ai      对接各家模型 Provider，把不同的流式输出驯化成统一事件
tau_agent   可移植的 Agent 内核：Harness、消息、工具协议、运行循环、事件流
tau_coding  应用与产品层：CLI、会话持久化、项目资源、本地编码工具、Textual TUI
```

```text
tau 命令行 / TUI
    → CodingSession（应用会话管理）
        → AgentHarness（通用 Agent 状态）
            → ModelProvider（统一模型接口）
                → 云端模型服务
```

模型返回的文本增量或工具调用，都顺着事件流往上走，最后被终端渲染、写入磁盘。**核心层 `tau_agent` 不知道外头是 Textual TUI、print mode，还是测试里的 Fake Provider。** 明天把 TUI 换成网页版，只要事件和循环没动，Agent 内核不必重写。

这张图后文不再重画。记住单向流动即可：产品层可以换，内核只认消息、工具和事件。

## 用一个真实请求建立直觉

设想您在终端里丢给 Tau 一句：

```text
找出 CLI 入口，并解释它如何启动会话。
```

Tau 不会把这行字直接推给模型然后坐等编造。后台大致是：

1. **应用层先准备**：`tau_coding` 打包 `AGENTS.md`、系统提示词、选定的模型、工作目录下的工具和历史会话；
2. **内核启动循环**：`tau_agent` 把问题塞进消息流，向模型发起流式请求；
3. **模型提出行动**：它发现自己看不见仓库，于是要求调用 `read` 去看 `src/tau_coding/cli.py`；
4. **本地执行**：Tau 读出文件，打成 `ToolResultMessage` 送回模型——送回去的是文件内容，不是模型的想象；
5. **再次推理**：模型基于真实代码生成解释，结束本轮。

开始、更新、工具执行、工具结果、结束等事件沿途产出。TUI 拿它画打字效果和工具指示器；print mode 拿它打文本；会话系统拿它追加进 JSONL。各取所需，不必各写一套循环。

**最小反例：** 把用户那句话直接 POST 给模型，再把返回文本打印出来。没有 `read`，模型只能猜仓库长什么样；没有事件流，终端也无法在工具执行中途取消。您得到的是会说话的补全，不是 Agent。Tau 后面每一篇，都在补上这里缺的那一层。

## 三分钟核对

不动手的话，上面这些只是又一篇博客。两个离线动作足够验证本篇的核心论点：

1. **看一眼真实的 Agent 事件流。** `uv run python notes/assets/run-slice/generate_slice.py | head -5`，用的是 Fake Provider，不碰任何真实模型 API。看开头几条：`agent_start` 开场、用户消息进流、assistant 消息接力——正文说的“反馈闭环”，在这几行里已经转起来了。
2. **跑 CLI 测试。** `uv run pytest tests/test_cli.py -q`，95 个测试全绿。`src/tau_coding/cli.py` 里 Typer 入口、`tau -p` print mode 这些本篇提到的家当，每个都有对应测试在背书。

## 怎样阅读本系列

如果只是想用 Tau 打工，翻 README 装环境、配 key 即可，不必先看源码。

如果想搞懂现代 Agent 的架构，Tau 是一张合适的解剖台。本系列不背诵 API，而是顺着一次请求，一层层看这套系统怎么设计。第 0 篇只负责地图；从第 1 篇起才下到具体文件。

下一篇《从一句话到一次行动》从 print mode 里这两行开始：

```python
async for event in session.prompt(prompt):
    renderer.render(event)
```

一行用户输入，怎样在 Python 里变成真实世界里的行动，从这里看起。
